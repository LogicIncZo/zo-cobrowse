# 0.3.7.0 — Zo Co-browse skill lifecycle: versioned product skill, install/update sync, server-side slimming

- **Date:** 2026-09-27
- **Status:** Draft — awaiting owner review
- **Slate:** 0.3.7.0 (feature train after 0.3.6.x; 0.9.0 stays the next major)
- **Owner decisions pinned at planning (2026-09-27):**
  1. Legacy repo `skill/` companion is **absorbed & retired** into the bundled skill.
  2. Read-only-turn awareness is **probe-first** — a live probe decides whether a pointer rides read turns.
  3. Skill layout is **SKILL.md + references/** (progressive disclosure), not a single file.
  4. The #239 follow-up (**systemPrompt moves server-side via persona_id**) is **in scope**, spike-gated.

## Context

0.3.0 shipped the versioned "cobrowse protocol" skill (#235, PR #248): the extension bundles
`extension/skills/zo-cobrowse/SKILL.md`, installs it into `/home/workspace/Skills/zo-cobrowse/` via
MCP `write_file` + canary read-back (one-shot ask fallback), and slims the action-turn tail to a
pointer + envelope demand once verified — invariant: **never lighter than the verified install**.
Action-turn tails sit at ~89 tok (down from ~259).

Three gaps motivate this slate:

1. **Timing.** The install check is lazy — first action turn of a session, once per extension
   version. The skill does not install/update when the extension does; a user who installs the
   extension and never sends an action turn never gets the skill, and Zo's awareness lags the
   shipped version until the first action turn.
2. **Scope.** The skill carries only the action protocol. Zo has no server-side knowledge of the
   product surface — Modes, bang commands, recipes/handoff/compose, context tiers, chat tabs,
   pickers — so feature guidance either rides per-turn prompts (token cost) or doesn't exist
   (Zo can't recommend `!recipe record` or pick `get_form` vs `read_page` well).
3. **Debt.** The repo's `skill/` directory (personas + preset library) predates the Mode system,
   is never auto-installed, is not versioned, and partially contradicts current behavior. It is
   dead weight that still shows up in AGENTS.md as a component.

## Goals

- The skill installs/updates **when the extension installs/updates** (`chrome.runtime.onInstalled`),
  with the existing lazy check retained as fallback.
- The bundled skill expands to the **full feature catalog** so Zo natively knows what the product
  can do and how each feature is triggered — read on demand, zero per-turn cost.
- **Prompt budget never grows** to explain features: new canon lands in reference files, enforced
  by the existing prompt-budget gate (verify stage 4/4).
- The per-turn `systemPrompt` moves server-side via **persona_id** (spike-gated, #239 follow-up).
- One versioned skill, one source of truth: legacy `skill/` retired.

## Non-goals

- No change to the action protocol itself (envelope, actions, cue ladders) — content moves, never
  rewrites.
- Safety rules (`SHARED_SAFETY_RULES`) stay **inline on every action turn** — they never move
  server-side (existing invariant, unchanged).
- No cross-tab DOM actions, no new user-facing features on the extension surface.
- No backend/relay work; no web-store listing work.

## Design

### 1. Skill package — `extension/skills/zo-cobrowse/` goes multi-file

```
extension/skills/zo-cobrowse/
├── SKILL.md                    # lean overview + feature catalog index
└── references/
    ├── protocol.md             # today's SKILL.md content, verbatim
    └── features.md             # the product-surface canon (new)
```

- **`SKILL.md`** (target ≤ ~60 lines): what the extension is; a one-line-per-feature catalog
  (capability → how Zo uses or recommends it); pointers into the references ("read
  `references/protocol.md` for the action protocol", etc.). Frontmatter keeps `name: zo-cobrowse`
  (workspace path and the `cobrowse-protocol-skill` marker are **stable** — e2e and tests route on
  them), an updated `description` covering the full product, and the `metadata.version: "0"`
  placeholder that `injectVersion` rewrites from the manifest at install time.
- **`references/protocol.md`**: the current SKILL.md body, byte-identical on the move (envelope,
  action grammar, pull actions, cue ladders, pacing). Pure relocation — evals and the slim-tail
  pointer keep working against the same canon.
- **`references/features.md`**: the new canon, one section per surface —
  - Modes: the 5 builtins (what each is for, context tier behavior) + custom Modes + Settings
    editing; how intent downgrade flips action turns to reads.
  - Bang commands: `!context`, `!handoff`, `!recipe run/compose/record/save`, `!summarize` —
    when Zo should recommend each in prose (e.g., user describes a repeatable flow → suggest
    `!recipe record`).
  - Context tiers + the opt-in DOM policy: what tiers 0–3 attach, why read turns are URL-only,
    the pull actions as the escalation path (already in protocol.md — features.md covers the
    policy, protocol.md the mechanics).
  - Tabs: chat tabs, `## Referenced Tabs`, `read_tab{ref}` — context-only, no cross-tab actions.
  - Pickers & surfaces: `/` skills, `%` workspace files, `@` tab refs, 📷 image toggle,
    write-assist popover — Zo cannot drive these UIs; it should know they exist so its guidance
    and `done{response}` prose are accurate.
  - Recipes & handoff: deterministic playback, human checkpoints, the **no-auto-submit rule**,
    compose parks, handoff boundaries (`readonly`/`no-submit`/`compose`), budget pauses — what Zo
    must never propose (e.g., emitting submit-ish clicks in a handoff continuation).
  - Diagnostics: Debug mode ring + share (user-triggered only).
- **Versioning:** skill version = extension manifest version (all four segments). Every release
  ships the skill; `injectVersion` stamps SKILL.md at install. Reference files need no individual
  versions — the install decision is keyed on SKILL.md's version and rewrites **all** files on
  mismatch (see §2). The bundled placeholder (`version: "0"`) and the file inventory get a
  version-sync lint (§4).
- **Zo-side discoverability:** `name`/`description` frontmatter is what the `/` skills picker and
  any Zo-side skill listing surface. The updated description is what makes the skill discoverable
  as "the product manual," not just "the action protocol."

### 2. Sync lifecycle (background.js)

- **Proactive:** `chrome.runtime.onInstalled` — for reasons `install` and `update` — calls the
  sync once, fire-and-forget (failures logged, never blocking; the handler already does content
  reinjection on update and stays cheap). `chrome_update`/`shared_module_update` reasons are
  ignored (extension version unchanged → lazy path is a no-op anyway).
- **Lazy fallback retained:** `ensureProtocolSkill()` stays exactly where it is (both ASK_ZO
  paths, once per version per session). It covers the dominant fresh-install case (no Zo token
  configured yet at onInstalled time) and any MCP hiccup at install time.
- **Install decision (version-keyed, unchanged in spirit):** read installed SKILL.md via MCP
  `read_file` → frontmatter version equals the extension version → skip everything (one read per
  version per session). Missing/unparseable/different → fetch each bundled artifact via
  `chrome.runtime.getURL`, `injectVersion` SKILL.md, `write_file` per file (the recipe-export
  multi-file pattern at background.js:3971), then canary read-back of SKILL.md. Read-back failure
  → state `installed:false`, inline tail stays. One-shot ask fallback (`oneShotWorkspaceWrite`)
  remains the MCP-down path for SKILL.md; references are best-effort (a missing reference degrades
  gracefully — SKILL.md tells Zo they exist and the pointer still names protocol.md).
- **State:** `SKILL_STATE_KEY` record grows per-file status:
  `{ installed, checkedVersion, version?, via?, reason?, files?: {path, ok}[] }` — **new Zod
  schema** in `tests/schemas/` (first contract for this state; none exists today). The sidepanel
  inspector reads the same key (unchanged pattern).
- **No per-file content hashing:** version match ⇒ trust. The residual risk (locally corrupted
  file at matching version) equals today's single-file risk and doesn't justify N reads per check.

### 3. Prompt slimming

- **Action turns:** the slim tail keeps its shape — `SKILL_POINTER` + `ACTION_ENVELOPE_DEMAND` +
  `SHARED_SAFETY_RULES`. `SKILL_POINTER`'s sentence is updated to name the references
  ("…grammar, cue ladders, pacing — see `references/protocol.md`; product features are catalogued
  in `references/features.md`"). Net token delta ≈ zero; the pointer was always one sentence.
- **The efficiency thesis:** with the feature canon server-side, feature knowledge stops being a
  per-turn prompt cost — for existing features (the catalog) and future ones (0.9.0 features ship
  as reference-file updates, still version-gated, zero prompt growth). The prompt-budget gate
  (verify stage 4/4) enforces "no per-turn growth" mechanically.
- **persona_id lane (spike-gated):** after a verified skill install, the background ensures a Zo
  persona exists whose prompt text matches the extension's system framing (ZO_PERSONA + the
  cobrowse system line — the exact string built from `lib/modes.js`, so byte-drift fails closed
  to inline). `create_persona{name,prompt}` → id cached in `storage.local`; turns pass
  `persona_id` and the inline `system` section drops. Live-verified facts this builds on:
  personas compose server-side with inline text (0.3.0 spike, #239 GO). **Spike must verify
  before build:** (a) persona composition with *custom-Mode* inline system text (no collision,
  sane ordering), (b) persona_id survives thread rotation. **Fail-closed rule:** any persona
  create/lookup/composition doubt → inline systemPrompt rides (never lighter than verified).
  A `delete_persona` cleanup runs on drift (system string changed ⇒ recreate, delete old id).
- **Read turns (probe-gated):** one live probe (`scripts/` probe script, house probe style):
  workspace has the skill installed; ask Zo a question answerable only from it ("which bang
  command records a repeatable workflow?") with NO pointer. Auto-discovery → read turns ship
  unchanged. No → a minimal pointer line rides read turns (~25 tok, mirrored in the inspector
  like the action-turn tail today). Either outcome is recorded in the ticket with probe evidence.

### 4. Legacy `skill/` absorption & retirement

- Absorb still-live canon: persona framing into SKILL.md's overview; the preset library is
  already superseded by `BUILTIN_MODES` + `presetToMode` (Modes are the extension-side preset
  system; `references/features.md` documents them). Nothing in `skill/SKILL.md`'s personas
  section reflects current persona routing accurately — it is rewritten, not copied.
- Delete: `skill/` (SKILL.md, references/presets.md, scripts/sync-presets.ts,
  assets/default-presets.json).
- Update references: AGENTS.md (the `skill/` row and the "Edit Zo-side presets/personas" table
  row → point at `extension/skills/zo-cobrowse/`); historical spec docs are NOT edited.
- Verify nothing imports them (grep gate in the PR; `sync-presets.ts` has no test coverage —
  it validates-and-prints by design).

### 5. Observability

- **Prompt inspector:** already shows skill install state — extend to show the version and,
  on failure, the reason (the state record already carries both).
- **Options → About card:** one line, "Zo skill: v`<version>` installed (mcp|ask) / not installed
  (reason)" — read-only, from the same state key. No new settings.
- **Debug ring:** a `skill_sync` kind (metadata-only: version, via, per-file ok, durations) —
  fits the privacy contract in `lib/debug-log.js`.

| E2E (`e2e/`) | mock-zo serves workspace-skill fixtures; update-path spec preseeds an old installed version and asserts rewrite + slim tail; slim-tail assertions keep routing on the stable marker |
| Evals | prompt change ⇒ cache stale ⇒ `bun run evals` red ⇒ refresh via `evals:live` (ZO_API_KEY), case ids stable (standing rule) |
| Gates | prompt-budget (verify stage 4/4): action-turn tail ≤ current budget; `bun run verify` + full e2e before merge |

## Risks & mitigations

| Risk | Mitigation |
|---|---|
| Zo does NOT auto-discover workspace skills on read turns | Probe-first decision gate; worst case is a ~25 tok pointer, mirrored in the inspector |
| persona_id composition misorders/conflicts with custom Modes | Spike gate before build; fail-closed to inline systemPrompt |
| MCP unavailable at install time | Lazy fallback on first action turn; one-shot ask fallback retained |
| Half-written multi-file install (crash mid-write) | Version-keyed decision: next check sees stale/missing SKILL.md version ⇒ rewrites all files |
| Reference files drift from shipped behavior | Every feature PR that changes catalogued behavior updates `features.md` in the same PR (AGENTS.md rule); version bump forces reinstall |
| Legacy `skill/` deletion breaks something unknown | grep gate in the PR; no imports exist today (verified at planning) |
