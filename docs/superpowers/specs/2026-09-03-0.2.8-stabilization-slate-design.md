## Intent

0.2.0–0.2.7 shipped a large surface fast (co-browse core, form-fill safety gate, chat UX, pickers, write-assist, handoff runs, observability). 0.2.8 is **not a feature release**: it is a stabilization bash — systematically verify everything already shipped, fix what's broken, and ship each fix as its own small point release. Stabilization through verification and fixing; no cap on point-release count (0.2.8.1 … 0.2.8.N "or more").

## 1. Versioning policy (4-segment)

`MAJOR.MINOR.PATCH.STAB`

- The 4th segment carries **stabilization fixes only — never features** (features → MINOR, e.g. the **0.9.0** feature release; breaking → MAJOR).
- Git tags: `v0.2.8.1`, `v0.2.8.2`, … — `.github/workflows/release.yml` already triggers on `v*`, no workflow change needed.
- `extension/manifest.json` `version` carries all four segments (Chrome-native; Chrome accepts 1–4 dot-separated integers). `version_name` mirrors it. `package.json` version is kept in sync (existing release-prep lint gate enforces this).
- Policy documented in `CONTRIBUTING.md` (§ Branching model, rule 4) and `AGENTS.md` (§ Branching & release flow) so agents stop assuming 3 segments.

## 2. 0.2.8.0 — the enabler release (conversation-id debug tooling)

The bash's own tooling ships first: when triaging a bad session you need the Zo conversation id — to paste into a bug report or to open the thread in Zo's web UI and see what Zo actually received.

**Zo web deep link (owner-confirmed 2026-09-03):** `https://<user-slug>.zo.computer/?chat=<conversation_id>&t=chats` — e.g. `https://cashlessconsumer.zo.computer/?chat=con_ijM6neD936odlluG&t=chats`. The slug is per-account and **not derivable from the API token** (public API has only `/zo/ask`, `/models/*`, `/personas/*` — no profile or conversation-read endpoints), so the origin is user-configured.

### 2.1 `extension/lib/zo-links.js` (new, pure ES module)

- `zoChatUrl(origin, conversationId)` → URL string or `null`.
  - Origin: trimmed; must parse as `http(s)`; trailing slash normalized; empty/null → `null`.
  - Conversation id: must match `^con_[A-Za-z0-9_-]+$` (real ids look like `con_ijM6neD936odlluG`; note `extension/AGENTS.md` historically says `conv_` — reality is `con_`; keep the pattern loose on length). Missing/malformed → `null`.
  - Result: `` `${normalizedOrigin}/?chat=${encodeURIComponent(id)}&t=chats` ``.
- `truncateId(id)` → display form for the chip (e.g. first 10 chars + `…`).
- Callers hide the affordance on `null` — no dead links, ever.
- Zod contract: `tests/schemas/zo-links.ts` (house pattern: every lib module under schema).

### 2.2 Config: `zoWebOrigin`

- `DEFAULTS.zoWebOrigin: ''` in `extension/lib/config.js`; persisted to `chrome.storage.sync` — it is the user's own account slug, not a credential (the API token stays `storage.local` per `SENSITIVE_KEYS`).
- Options → **Connection** card gains a "Zo web origin" field. Hint: `e.g. https://cashlessconsumer.zo.computer — the host of your Zo chat URL; enables "Open in Zo" links`. Empty = feature off. Non-empty must parse as http(s) URL or Save flags it (existing dirty-marker/toast flow).

### 2.3 Sidepanel affordances (no new message types)

- **Assistant footer chip:** next to the existing 🔗 context-tier chip, a muted `#con_ij…` chip renders on assistant messages whose conversation has a `zoThreadId` (mode/model already repeat per footer — density-consistent). Tooltip = full id + "click to copy". Click = copy full id via the existing footer-Copy clipboard path + feedback.
- **↗ Open in Zo** icon renders only when `zoWebOrigin` **and** `zoThreadId` both exist → `chrome.tabs.create({ url: zoChatUrl(…) })`. The sidepanel already holds `tabs` permission and `zoThreadId`; background.js and `tests/schemas/messages.ts` are untouched.
- **History cards:** the same two actions (copy id, open in Zo) join ✎/⬇/🗑 per card, using that conversation's `zoThreadId`.
- **Handoff note:** the chip always copies the conversation's real Zo thread id — not derived run sessionIds — that's the thread visible in Zo's UI.

Every shipped surface × how it gets verified. Assets exist; the bash **runs** them and records results.

The matrix is maintained in the implementation plan (`docs/superpowers/plans/2026-09-03-0.2.8-stabilization.md`) with per-round checkboxes; QA_REPORT.md logs each round's findings.

## 4. The per-bug loop (one fix = one point release)

1. **Find** → GitHub issue on milestone `0.2.8`, `bug` label, evidence attached (file:line, trace, conversation id, diagnostics export).
2. **Fix** → `fix/*` branch from dev → PR → CI + e2e green → merge to dev.
3. **Ship** → `chore(release)` bumps manifest+package to the next `0.2.8.N` → dev→main PR → tag `v0.2.8.N` on main → release.yml publishes the zip.
4. **Record** → QA_REPORT.md round entry; CHANGELOG `[Unreleased]` accumulates and stamps at each point release.

Default: **one fix = one point release**. Batching two same-day typo-class fixes into one release is allowed but explicit (say so in the release PR). Feature-sized work never rides a `.N` bump — it waits for 0.9.0.

## 5. Exit criteria (when the bash ends)

- One full manual-panel-checklist pass green, **and**
- a week of real owner usage with no new P1/P2 findings, **and**
- unit/e2e suites + prompt evals green.

Then the bash closes and the version train moves to **0.9.0** (feature slate: #46–#54 plus the autonomy-foundation issues #124–#131, which moved off this milestone on 2026-09-03 — unaffected by this spec).
