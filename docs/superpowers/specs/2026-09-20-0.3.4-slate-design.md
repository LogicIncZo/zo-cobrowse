## Part A — Jev support (TypeSafe AI "System One model")

### What Jev is (research, 2026-09-20)

[Jev](https://jevai.net) is the first "System One model" from [TypeSafe AI](https://typesafe.ai)
(built by Diogo Almeida, a ChatGPT co-inventor; early access). Unlike an LLM it does not
generate text: it takes unstructured **state** plus pre-declared **questions** and returns
**typed, probabilistic decisions** — choices, scores, and yes/no probabilities — in
**70–500 ms** end-to-end (vendor claim: 40–200× faster than frontier LLMs, ~444× cheaper on
decision tasks; input $0.042/MTok, output tokens free). Training is RLCD ("Reinforcement
Learning for Calibrated Decisions"); sampling is fully parallel, so batching extra questions
into one call barely moves latency. Outputs are constrained to the declared schema with
calibrated confidence — the vendor's "zero hallucination / no type errors" pitch.

Key properties that matter for us:

- **No text generation at all** → fill values, prompt composition, summaries stay with Zo.
  Jev only answers questions we pose about state we supply.
- **Choice criteria cap = 255 options** → fits our tier-2 clickable-element candidate lists.
- **Questions evaluate in parallel against the same state** → one call can carry the
  click-target choice AND the goal-done check for a turn.
- **Calibrated confidence** → the documented
  [confidence-routing pattern](https://docs.typesafe.ai/patterns/confidence-routing):
  act above a threshold, escalate to the slow path (Zo) below it. This is the seamless
  integration story: Jev is a fast path with a full Zo fallback, never a replacement.

Sources: [announcement](https://typesafe.ai/blog/introducing-system-one-models-and-jev) ·
[product page](https://jevai.net) · [HTTP API reference](https://docs.typesafe.ai/api) ·
[harness patterns (LangChain)](https://www.langchain.com/blog/building-a-harness-with-jev) ·
[JS SDK](https://docs.typesafe.ai/sdk/javascript.md)

### API contract (docs.typesafe.ai/api, captured 2026-09-20)

```
POST https://api.typesafe.ai/v1/systemone
Authorization: Bearer <TYPESAFE_API_KEY>
Content-Type: application/json
```

Request (all fields required):

```json
{
  "model": "jev-latest",
  "state": "…page state / structured object…",
  "questions": {
    "target": {
      "type": "choice",
      "instructions": "Which element should be clicked to …?",
      "criteria": { "e3": "Buy button — submits the cart", "e7": "Size M — selects a shirt size" }
    },
    "goal_done": {
      "type": "noul",
      "instructions": "Is the user's goal already achieved on this page?"
    }
  }
}
```

- `state` accepts string, object, or array — we can send our structured capture directly.
- Question types: `noul` (yes probability), `choice` (criteria map, ≤255 options),
  `score` (ordered criteria, 2–10 levels). `instructions` may reference `state` fields
  in backticks.

Response:

```json
{
  "model": "jev-1.13.0",
  "answers": {
    "target":    { "type": "choice", "choice": "e3",
                   "probabilities": { "e3": 0.88, "e7": 0.12 }, "confidence": 0.81 },
    "goal_done": { "type": "noul", "noul": 0.95 }
  },
  "usage": { "input_tokens": 296, "output_tokens": 20 }
}
```

Errors: `401` bad key · `422` validation (body names the field) · `429` rate limit ·
`529` overloaded — retry 429/529 with exponential backoff (SDK default behavior; we
reimplement in the background worker since we use plain `fetch`, matching our
hand-rolled Zo transport — no SDK dependency, same reasoning as the 2026-08-28
zocomputer-ts verdict).

### Where Jev fits in the agentic loop

The pain: every navigation decision is a full Zo turn (seconds). Jev turns the
*mechanical* decisions into sub-second calls and leaves *reasoning* to Zo.

| Hook | Question | Primitive | On low confidence / error |
|---|---|---|---|
| **Click-target pick** — Zo's click cue missed or is ambiguous; tier-2 candidates exist | "Which candidate matches the intent?" (candidate labels as criteria) | `choice` | full Zo turn / healer as today |
| **Done-gate** — before a chained continuation turn (handoff, compose, multi-action turns): "re-ask Zo, or are we done?" | "Is the user's goal already achieved on this page?" (url+title+text excerpt as state) | `noul` | chain the Zo turn as today |
| **Intent routing** — sharpen `detectIntent()` heuristics | "Is this read-only or an action request?" | `choice` | keep heuristic result |

All hooks: gated behind `jevEnabled` (default **off**), one shared `jevMinConfidence`
threshold (default 0.8), hard 2.5 s timeout, single backoff-retry on 429/529, and any
failure silently falls back to the Zo path — the extension must behave exactly as today
when Jev is off or down.

### Non-goals (v1)

- No fill-value generation, no text generation of any kind (impossible by design).
- No Jev-only autonomous mode; Zo remains the planner, Jev a bounded decider.
- No stream interruption — Jev calls happen before a Zo turn or between actions, never
  mid-stream.

### Privacy & trust boundary

Configuring Jev sends page state to a **second processor** (TypeSafe AI) in addition to
Zo. Required handling, consistent with the 0.3.0 security round:

- Opt-in only (`jevEnabled` default off), the options card states where state goes.
- State builder **strips all form-field values** and redacts sensitive fields — reuse the
  `lib/formfill.js` sensitivity heuristics + `redactValue` so secrets never reach Jev.
- `PRIVACY.md` + the options privacy copy gain a Jev paragraph when the feature ships.

### Risks

- **Early access**: agent-facing access is waitlist-gated; the feature ships dark (off)
  until the owner holds a key. Gates must be runnable against a local mock.
- **Model pinning**: `jev-latest` is an alias; upstream publishes per-version notes
  (e.g. jev-1.13 "model jaggedness"). Ship `jevModel` default `jev-latest`, overridable —
  same posture as our Zo model select.
- **Pricing sustainability**: vendor's own caveat; irrelevant at our per-turn volume, and
  the feature is off by default anyway.

## Part B — Settings rationalization: Zo username + token

### Current state (audit, 2026-09-20)

Connection pane (`extension/options.html` `#card-connection`) asks for four things:

| Field | Storage | Actually… |
|---|---|---|
| Zo Access Token | `zoAccessToken` (local, sensitive) | the real credential — keep |
| API Endpoint | `zoApiUrl` (sync) | constant for everyone: `https://api.zo.computer/zo/ask` |
| Zo.space Endpoint | `zoSpaceEndpoint` (local, sensitive) | mechanically `https://<slug>.zo.space` — and the *default* is hard-coded to the owner's own space (`cashlessconsumer`), which every fresh install silently inherits |
| Zo Web Origin | `zoWebOrigin` (sync) | mechanically `https://<slug>.zo.computer` — exists only because an API token does not encode the slug (owner-confirmed 2026-09-03) |

Three of the four fields are derivable from one fact the user already knows: their Zo
**username slug** (the `cashlessconsumer` in `cashlessconsumer.zo.space` /
`cashlessconsumer.zo.computer`). The owner's ask — "just ask Zo username and token" — is
therefore mechanically exact.

### Target state

- Connection card asks **Zo Username** + **Zo Access Token**, plus Test Connection.
- New `zoUsername` (storage.sync, slug-validated `[a-z0-9-]+`); on change, derived values
  are written to the existing keys (`zoSpaceEndpoint`, `zoWebOrigin`) so every consumer
  (`background.js` space queries, `lib/zo-links.js` deep links, sidepanel chips) is
  untouched.
- API Endpoint / Zo.space / Zo Web Origin move into a collapsed **Advanced** `<details>`
  (pre-filled with derived values; a manually set value wins over derivation — the
  override-not-rewrite rule, same as Mode overrides).
- **Migration**: users with non-default `zoSpaceEndpoint`/`zoWebOrigin` keep them
  (shown in Advanced as custom); the owner-specific default space endpoint is dropped for
  new profiles — empty username means no space endpoint, not someone else's.
- Onboarding copy (#313) updated to the two-field reality.

### Part C — One save button

Current buttons: **Save Settings** inside the Connection card (`options.html:329`) AND a
second **Save Settings** at the bottom of the form (`options.html:595`) — the same form,
two identical submits — plus the Prompts editor's scoped **Save** (`options.html:401`).

Target: exactly **one** Save Settings, rendered as a sticky bottom bar that carries the
existing dirty-tracking state (`.save-dirty` marker already exists; the two autosave
controls — model select, quick-action rows — stay excluded). The Prompts editor folds
into the same global save: its fields join the form's dirty tracking, Save persists the
per-mode override, and its scoped Save button is replaced by Reset (+ the live preview
it already has). Save-on-tab-switch behavior unchanged.
